# Развёртывание НейроМаркет на VPS через Claude Code

## Задача

Выпустить утверждённую версию агентства из `khmary63/khabarova`, ветка `codex/agency-rebrand-2026-10-02` (PR #2), на **neyromarket.com**. Работа на сервере не была выполнена в рамках подготовки пакета. Точные пути, порт, сеть Caddy и текущий способ запуска основного сайта необходимо определить на сервере.

Полный серверный исходный код находится в этой ветке. Превью в ChatGPT Sites — образец внешнего вида, а не серверный артефакт. В production нет баннера превью и имитации отправки формы. Материалы блога/портфолио берутся из существующей БД, а не из снимка данных.

## 1. Инвентаризация без изменений

1. Прочитать CLAUDE.md, этот документ и AGENCY-REBRAND.md.
2. Проверить состояние рабочего checkout и сохранить незакоммиченные серверные изменения отдельно. Не делать reset --hard поверх локальных правок.
3. Определить, кто обслуживает neyromarket.com: Caddy/nginx, Docker/systemd/PM2, активный каталог/симлинк, upstream и используемые порты. Прочитать конфигурацию домена, inspect/mounts контейнера и список сетей. Не печатать environment целиком, docker inspect.Config.Env и содержимое файлов секретов.
4. Проверить исходное состояние `/`, `/apps`, `/blog`, `/roi`, `/reviews`, `/contacts`, `/privacy`, `/msb`, `/b2b`, `/robots.txt`, `/sitemap.xml`, `/llms.txt`, один опубликованный URL статьи и отраслевой ROI URL.
5. Зафиксировать текущий commit, release path, Caddy/nginx конфигурацию, способ запуска, права каталогов и возможность отката. Сохранить резервную копию конфигурации и действующего артефакта. Резервное копирование БД выполнить штатным механизмом; не удалять/переинициализировать данные.
6. При доступе к Метрике, Вебмастеру и Search Console зафиксировать страницы входа и поисковые показатели до релиза. Отсутствие доступа отметить, не выдавать выдуманную проверку.

**Важно:** `.github/workflows/deploy-vps.yml` и `scripts/release.sh` публикуют **factory.neyromarket.com**. Их не запускать для выпуска основного сайта. Merge в main запускает существующий workflow Factory. Этот пакет не меняет автодеплой.

## 2. Получение кода

В отдельном каталоге сборки либо отдельном worktree, не поверх действующего артефакта:

```bash
git clone --branch codex/agency-rebrand-2026-10-02 --single-branch https://github.com/khmary63/khabarova.git neyromarket-release
cd neyromarket-release
git rev-parse HEAD
```

Если репозиторий уже клонирован — использовать обычные git fetch и отдельный worktree нужной ветки. Использовать существующую GitHub-аутентификацию; не вставлять токены в URL или команды. Зафиксировать SHA кандидата на выпуск и не менять его между проверкой и публикацией.

## 3. Окружение

Node 22, Bun с поддержкой существующего текстового `bun.lock` (в текущем workflow используется latest), Bash/GNU coreutils. Docker Compose v2 нужен только для варианта контейнерного запуска ниже. Версии фактически использованных Node/Bun записать в отчёт релиза. Не обновлять зависимости через update и не создавать новый lockfile.

### Публичные настройки во время сборки

Сохранить значения действующего сайта. Используются:

- `VITE_SUPABASE_URL` — URL существующего Supabase-проекта;
- `VITE_SUPABASE_PUBLISHABLE_KEY` — существующий публичный/anon ключ для браузерного клиента.

Это публичные параметры. Нельзя подставлять service_role вместо publishable ключа. Если параметры загружаются из `.env`, файл держать вне Git, права 600. Не копировать в сборку все секреты сервера без необходимости.

### Серверные настройки во время запуска

Шаблон: `deploy/main.env.example`. Использовать существующие значения:

- `SUPABASE_URL`;
- `SUPABASE_SERVICE_ROLE_KEY` — только сервер;
- `SUPABASE_PUBLISHABLE_KEY` — серверные auth middleware;
- `CRM_WEBHOOK_TOKEN` — секрет существующего webhook личной CRM Марии.

Не создавать новый Supabase-проект и не переключать базу. Наличие ключей проверять без вывода значений. Также сохранить прочие переменные текущего приложения (например, для существующих AI/API функций). Никакой миграции БД для ребрендинга не требуется. Не выполнять reset БД.

Webhook заявок: `POST https://crm.neyromarket.com/api/webhook/leads`, заголовок `Authorization: Bearer …`. Контракт ранее прочитан в `khmary63/crm`; перед живым выпуском сверить актуальный контракт, если CRM менялась. Репозиторий CRM изменять не требуется.

## 4. Сборка

```bash
bash scripts/build-main.sh
```

Скрипт временно заменяет приватный registry Lovable в bun.lock на npmjs, устанавливает зависимости с frozen lockfile, проверяет TypeScript и тесты CRM с имитацией ответов, собирает Node SSR. Исходный lockfile восстанавливается через trap. Тесты не отправляют настоящих заявок.

Если каталог уже подготовлен с зависимостями, эквивалентные проверки:

```bash
bunx --no-install tsc --noEmit
bun test tests/agency-leads.test.ts
VPS_BUILD=1 bun run build
test -f .output/server/index.mjs
test -d .output/public
```

Результат — **вся `.output/`**, включая `server/` и `public/`. Сервер запускается `node .output/server/index.mjs`. Не обслуживать этот релиз как SPA с index.html fallback: серверные функции, SSR, sitemap и POST формы должны работать.

## 5. Проверка кандидата до переключения домена

Запустить кандидата на свободном loopback-порту с серверным окружением. Использовать реальную существующую БД только для чтения. Staging закрыть от внешнего доступа; если выводится в отдельный домен — защищать авторизацией и X-Robots-Tag noindex, не менять production robots.txt ради staging.

Проверить:

- Главная и три направления HTTP 200, текст присутствует в HTML до JavaScript, один H1, canonical на https://neyromarket.com с правильным путём.
- Выбор трёх вкладок меняет URL и весь контент; обновление страницы сохраняет направление.
- Два вопроса → содержательные рекомендации без телефона; проверить три ветки каждого направления и повторное прохождение.
- Десктоп/телефон: меню, формы, отсутствие горизонтального переполнения, изображения, анимации и режим reduced-motion.
- ROI: пройти квиз, получить расчёт, проверить отраслевой URL и query результата.
- Портфолио: данные и галереи из существующей БД; блог: список, фильтры, статья; отзывы и контакты.
- Форма: без согласия/с неверными данными запрос отклоняется. При ошибке CRM не показывается успех.
- Настоящая тестовая заявка — только в рамках проверки релиза с пометкой «Тест развёртывания». Убедиться, что карточка появилась в личной CRM, направление/срок/UTM верны, сумма 0. Токен не раскрывать. Не запускать массовые тестовые заявки.
- Noya: существующий продавец загружается и кнопка его открывает. Обновить внешнюю базу знаний по NOYA-AGENCY-KNOWLEDGE.md. Проверить запись на консультацию и передачу человеку отдельным тестом в кабинете Noya. Сам сайт не настраивает внешнего бота и не подтверждает уведомления Марии.

## 6. Выпуск: сначала выбрать фактический способ запуска

### Действующий основной сайт уже имеет процесс релизов

Предпочитать его: загрузить .output в новый каталог релиза, сохранить старый, переключить только upstream/симлинк/процесс основного домена штатным способом. Сохранить env, порт, сеть и TLS. Не переводить работающий nginx/PM2 в Docker без необходимости. Команды перезапуска брать из обнаруженной конфигурации, не угадывать имя сервиса.

### Отдельная установка через Docker Compose

Использовать шаблон `deploy/docker-compose.main.yml`. Пример переменных (пути и порт — **предлагаемые**, предварительно проверить на сервере):

```bash
export NM_MAIN_BASE=/var/www/neyromarket-main
export NM_MAIN_COMPOSE=/opt/neyromarket-main/docker-compose.yml
export NM_MAIN_ENV_FILE=/opt/neyromarket-main/.env
export NM_MAIN_PORT=3010
export NM_MAIN_HEALTH_URL=http://127.0.0.1:3010/
export NM_RELEASE_SHA=$(git rev-parse --short=12 HEAD)
```

Создать отдельные каталоги, скопировать compose, заполнить runtime env из действующего окружения, поставить env права 600. Не переиспользовать каталоги Factory. Эти shell-переменные нужны Compose при каждом запуске и откате: сохранить несекретные пути/порт в отдельном deployment-конфиге вне Git либо экспортировать заново.

```bash
docker compose -f "$NM_MAIN_COMPOSE" config --quiet
bash scripts/release-main.sh deploy .output
```

Скрипт создаёт каталог релиза, атомарно меняет current, перезапускает только neyromarket-main, проверяет HTML главной и откатывается на предыдущий релиз при ошибке. Старые релизы не удаляются автоматически. На первой установке предыдущего релиза нет: при ошибке новый контейнер останавливается; работающий сайт до проверки и переключения upstream остаётся на старом процессе.

Caddy на хосте: upstream — `127.0.0.1:3010` (подставить выбранный порт). Caddy в контейнере: добавить **обнаруженную** внешнюю сеть через локальный compose override и использовать `neyromarket-main:3000`; localhost внутри контейнера — не хост. В таком случае release-main.sh нужно вызывать с COMPOSE_FILE-набором либо записать единую итоговую compose-конфигурацию в NM_MAIN_COMPOSE, потому что скрипт принимает один файл. Проверить DNS имени в сети и `caddy validate` перед reload. Не менять доменные блоки других сервисов.

Переключить **только neyromarket.com и его существующий www-редирект**, когда кандидат прошёл проверки. Сохранить TLS, заголовки, лимиты и передачу Origin/Host/forwarded headers. Не перенаправлять API заявок на сторонний домен. После публичного переключения повторить проверки HTTP/формы/виджета.

## 7. SEO и GEO

Сохранить маршруты `/msb`, `/b2b`, `/factory`, `/roi`, `/roi/result`, отраслевые `/roi/*`, `/apps`, `/blog`, `/blog/*`, `/reviews`, `/contacts`, `/privacy`. Новые `/ai-creator`, `/automation`, `/lead-generation` — дополнение. Не ставить массовые редиректы на главную.

Сохранить файлы подтверждения поисковых сервисов и meta google-site-verification, существующий ID Метрики и остальные счётчики. Проверить robots без случайного Disallow:/noindex, sitemap со статьями и направлениями, canonical, JSON-LD Organization/Person/Service/FAQ и public/llms.txt. Не заменять полный sitemap статическим списком трёх страниц. Не редактировать subdomain factory/noya ради устранения дублей. Отслеживать поиск после релиза: сохранение URL не гарантирует неизменные позиции, llms.txt не гарантирует цитирование.

## 8. Откат

Для существующего процесса — возврат сохранённого upstream/артефакта и штатный restart. Для предложенной схемы:

```bash
# Повторно экспортировать тот же NM_MAIN_* deployment-конфиг.
bash scripts/release-main.sh rollback
```

Если это первая установка отдельного контейнера, вернуть прежний upstream основного домена и проверить его. Миграций БД нет, откат кода не должен стирать данные и заявки. После отката проверить основную страницу, блог, форму и HTTP статусы.

## 9. Отчёт Claude Code

Сообщить SHA, ветку, фактический путь релиза и способ запуска, что проверено, статус CRM/Noya/счётчиков, публичный URL и точную команду отката. Отдельно назвать непроверенные внешние интеграции. Не сообщать секреты и не считать успешную сборку доказательством сквозной доставки заявок.
